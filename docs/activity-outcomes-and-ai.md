# Ожидаемый результат, фактический результат и ИИ-планирование

Дата: 25 октября 2026 года.
Статус: согласованное направление продукта; проектное описание будущей реализации.

## 1. Ценность и основной сценарий

Активность объединяет занятия, измеримые результаты и историю прогресса. Пользователь задаёт, что хочет успеть за доступное время, фиксирует факт и получает заполненное предложение следующего плана.

**План занятия → выполнение → фиксация факта → сравнение → предложение ИИ → принятие или изменение следующего плана.**

Первым результатом реализации должен стать этот полный сценарий. Недельные обзоры и шаблоны затем используют те же данные.

## 2. Примеры

### Тренажёрный зал

Активность: «Тренажёрный зал». Доступное время конкретного занятия: 60 минут.

| Пункт | Ожидаемый результат из примера пользователя | Что пользователь записывает как факт |
| --- | --- | --- |
| Подтягивания | 4 подхода по 10 повторений | Реальное количество повторений в каждом подходе |
| Бег | 20 минут | Реальная продолжительность; дистанция — необязательно |
| Поднимание гири | 10 кг, 4 подхода по 10 повторений | Вес и повторения каждого выполненного подхода |
| Пресс | 4 подхода по 10 повторений | Реальное количество повторений в каждом подходе |

Это пример структуры учёта, а не назначение тренировочной программы.

Результат подходов хранится отдельно: запись «10, 10, 8, 6» информативнее одной отметки «сделано». Можно отметить пропуск, замену упражнения и необязательную причину. Для тренировочной рекомендации нужны цель, опыт, субъективная сложность, ограничения, доступное оборудование и сведения о восстановлении, необходимые для конкретного предложения.

Лимит 60 минут относится ко всему занятию. Оценка выполнимости учитывает работу, отдых и переходы, если эти значения известны. При недостатке данных приложение обозначает неопределённость, а не обещает, что набор упражнений точно поместится в час.

### Чтение

Активность: «Чтение». В плане выбирается конкретная книга или издание и доступное время.

Иллюстративный сценарий: перед занятием текущая страница 120, целевая страница 140; после занятия пользователь указывает страницу 136. По принятому соглашению подсчёта это план 20 страниц и факт 16 страниц. Следующий план начинается со страницы 136. Если пользователь хочет сначала закончить прежний отрезок, остаётся 4 страницы.

Объём страниц не показывает понимание материала. Необязательная заметка помогает сохранить результат чтения без превращения занятия в обязательный экзамен. Изменение темпа зависит от цели пользователя; завершённый план не обязывает увеличивать число страниц.

## 3. Модель предметной области

| Сущность | Назначение |
| --- | --- |
| Activity | Долгоживущая активность, её тип и цель: тренировка, чтение или общий список |
| ActivityPlan | Версия плана конкретного занятия: активность, дата, часовой пояс, бюджет времени, источник и состояние |
| PlanItem | Упражнение, отрезок чтения или другой пункт; порядок, ожидаемые показатели и ссылка на предмет |
| ActivitySession | Учёт времени; необязательная ссылка на план. Несколько сессий могут выполнять один план |
| OutcomeRecord | Фактические показатели пункта, состояние выполнения, источник и необязательная заметка |
| Book / Exercise | Устойчивая идентичность книги/издания или упражнения для сопоставления истории |
| PlanSuggestion | Предложение ИИ: исходные версии данных, объяснение, изменения и полностью заполненный проект следующего плана |

DayPlan продолжает объединять занятия по датам. DayPlanItem связывает активность с планом конкретного занятия. Ожидаемый результат хранится в этом плане, а не как изменяемый набор упражнений сразу для всех прошлых и будущих занятий активности.

Для первого выпуска можно сохранить текущую уникальность «план дня + активность»: один план активности на день, несколько сессий для его выполнения. Несколько самостоятельных планов одной активности в один день потребуют отдельного изменения этого ограничения.

Существующие сессии сохраняются без вымышленных результатов. Запуск без плана остаётся возможным; такой учёт не получает автоматически придуманный чек-лист.

### Типы показателей

Начать с трёх шаблонов:

- **Тренировка:** силовое упражнение с массивом подходов либо упражнение на продолжительность; повторения, вес, время и дистанция имеют явные единицы.
- **Чтение:** книга/издание, исходная и целевая страница, фактически достигнутая страница.
- **Общий список:** пункты с отметкой выполнения и необязательным числовым показателем из ограниченного набора единиц.

Ожидания и факт валидировать раздельными схемами в shared. Для структурированных полей допустим JSONB с типом и версией схемы; ссылки, принадлежность пользователю, порядок и состояния остаются явными полями модели. Не создавать универсальный конструктор произвольных форм в первом выпуске.

## 4. Правила целостности и сравнения

- Зафиксированная версия плана сохраняется вместе с результатом. Изменение шаблона не переписывает прошлые цели.
- После начала занятия изменения плана видны отдельно от исходного ожидания. Факт никогда не подменяется запланированными значениями.
- «Не записано», «пропущено», «частично выполнено» и измеренный нулевой результат различаются.
- Время и результат независимы: истечение часа не подтверждает выполнение упражнений или чтение страниц.
- Не складывать килограммы, повторения, минуты и страницы в единый процент прогресса. Сравнение показывать по пунктам и однородным показателям.
- Для тренировок сравнивать одни и те же упражнения и варианты исполнения, сохраняя данные каждого подхода. Изменение веса и количества повторений показывать отдельно.
- Для чтения сохранять одну систему отсчёта страниц, различать издания, проверять границы книги, если они заданы. Повторное чтение учитывать отдельно; отсутствующий результат не продвигает текущую страницу.
- Результат принадлежит плану занятия. При пересечении полуночи время распределяется по локальным дням, а пункты плана не дублируются в двух днях.
- Исправление результата сохраняет новую версию и помечает зависимое предложение ИИ как устаревшее.
- Повторное нажатие «создать следующий план» не создаёт дубликаты.

## 5. Пользовательский интерфейс

### Подготовка

Выбрать активность, дату, доступное время и шаблон. Добавить пункты вручную, скопировать предыдущий план или выбрать предложение ИИ. Видеть список ожидаемых результатов и возможность изменить каждое значение.

### Выполнение

На экране занятия рядом с таймером показывать пункты плана. Для тренировки — быстрый ввод и отметка подходов; для чтения — ввод текущей страницы. Разрешить сохранять факт по ходу занятия и заполнить его после завершения. Ручное сохранение результата доступно и без запуска таймера.

### Завершение

Показать «ожидалось / получилось» по каждому пункту, записанное время и незаполненные результаты. Предложить уточнить пропуски и необязательную причину расхождения. Сохранение результата не требует обращения к ИИ.

### Следующее занятие

Кнопка «Предложить следующий план». Ответ содержит краткое объяснение, различия с предыдущим планом, выбранные пункты и оценки. Пользователь может принять, изменить или отклонить предложение и выбрать дату. После принятия появляется обычный заполненный план в календаре.

Ввод «план выполнен» может ускорять заполнение, но явно предлагает подтвердить скопированные значения как факт. Пустые результаты не заполняются из плана автоматически.

## 6. Как работает ИИ

1. Сервер проверяет владельца активности и собирает только относящиеся к предложению данные: цель, тип занятия, версии результатов, несколько сопоставимых прошлых занятий, доступное время и ограничения.
2. Программный расчёт формирует факты: показатели по пунктам, расхождения и полноту данных. Числовые итоги не передаются модели на самостоятельное вычисление.
3. Модель получает эти факты и возвращает структурированное предложение: объяснение, изменения, основания и проект нового плана.
4. Сервер проверяет схему ответа, ссылки на доступные книги/упражнения, единицы, границы показателей, полноту обязательных данных и действующие ограничения пользователя.
5. Предложение сохраняется отдельным черновиком. При принятии сервер повторно проверяет актуальность исходных данных и транзакционно создаёт план.

Для первого выпуска достаточно одного ограниченного сценария генерации. Провайдера и модель выбрать при реализации; текущие React, Hono, PostgreSQL и shared-схемы позволяют добавить такой сервис.

### Что ИИ может предложить

- Продолжить незавершённый план с актуальной точки.
- Повторить сопоставимый план для закрепления результата.
- Изменить объём, порядок или доступное время с объяснением причины.
- Для тренировки предложить изменение нагрузки в рамках проверенных правил и пользовательских ограничений.
- Попросить уточнение, если без него предложение недостоверно.

### Условия для тренировочной прогрессии

Правило «выполнил один раз — обязательно повысить нагрузку» не закладывать. Политика должна учитывать цель, несколько сопоставимых результатов, субъективную сложность, восстановление и ограничения. Варианты ответа включают сохранение, снижение и повышение нагрузки.

При сообщении о боли, травме или неподходящем самочувствии исключать автоматическое повышение. Медицинские назначения и реабилитационные программы не входят в первый выпуск. Конкретные правила прогрессии и допустимые изменения перед выпуском тренировочных рекомендаций проверить с квалифицированным специалистом; общие рекомендации не заменяют индивидуального решения.

Продуктовое решение о таких ограничениях соответствует акценту ACSM на индивидуальных целях, переносимости и безопасности программы; числовые правила прогрессии этим документом не устанавливаются.

### Ошибки, стоимость и обращение с данными

- При тайм-ауте, недоступности модели или неверном ответе результат занятия остаётся сохранённым. Пользователь может составить план вручную или скопировать прошлый.
- Повторная генерация и принятие используют отдельные идентификаторы операций; ограничить параллельные запросы и частоту повторов.
- Зафиксировать версию контекста, схемы и модели, объём использования и причину отказа валидации. Неполные и устаревшие данные явно обозначать.
- Объяснить, какие сведения передаются внешнему провайдеру. Не отправлять весь аккаунт, контактные данные и необязательные личные заметки.
- Применять ограничения доступа к планам, результатам, предметам и предложениям на сервере. Строки названий и заметок считать пользовательскими данными, а не инструкциями для модели.
- Сохранить продуктовую аналитику без содержания тренировок и заметок. Расходы на генерацию измерить до определения лимитов подписки.

## 7. Порядок реализации

| Выпуск | Что сделать | Проверяемый результат |
| --- | --- | --- |
| 0. Основа | Изоляция данных, часовые пояса, надёжность таймера | Истории и время пользователя достоверны |
| 1. Ручной полный сценарий | Планы занятий, пункты, ожидание и факт, шаблоны чтения и тренировки, сравнение и копирование | Оба примера пользователя выполняются без ИИ |
| 2. ИИ следующего занятия | Сервис предложения, структурированный ответ, проверка, объяснение, изменение и принятие | По сохранённому факту создаётся заполненный следующий план |
| 3. История и прогрессия | Несколько сопоставимых занятий, история изменений, проверенная политика тренировочных предложений | Рекомендация учитывает историю, ограничения и цель |
| 4. Недельный обзор и подписка | Обзор результатов, повторение планов, измерение полезности и расходов | Пользователи повторяют цикл и понимают платную ценность |

Внутри первого выпуска удобно начать с чтения: проверить связь «книга → план → факт → следующий план», затем добавить подходы и показатели упражнений. Это порядок инженерной реализации; оба типа входят в выбранное направление продукта.

## 8. Критерии готовности первого сценария с ИИ

- Пользователь создаёт тренировку из четырёх пунктов с лимитом времени и фиксирует каждый подход отдельно.
- Частичный результат и изменение веса сохраняются без потери исходного плана.
- Пользователь выбирает книгу, задаёт ожидаемый отрезок и фиксирует достигнутую страницу.
- Следующий план чтения начинается с подтверждённого факта и не выходит за известные границы книги.
- Предложение показывает основания; успешное занятие не вызывает обязательного усложнения.
- Невалидный ответ модели не становится планом. Исправленный факт делает старое предложение неактуальным.
- Подтверждение создаёт один новый план на выбранную дату; отказ ничего не меняет в календаре.
- Ошибка ИИ не блокирует ручной сценарий и не теряет результаты.
- Закрыты проверки доступа, повторных запросов и несогласованных единиц; выполнены сценарии неполных данных и нескольких сессий одного плана.

В пилоте измерять повторное заполнение факта, долю принятых и исправленных предложений, причины отказов, создание следующего занятия и возвращение к нему. Одного принятия рекомендации недостаточно для вывода о пользе или реальном росте показателей.
